# 内容库近重复检测

我们做内容库的去重。库里几百万篇东西，转载和轻微改写的特别多，完全按文本相等去重只能抓到一小部分；之前试过两两比相似度，跑了两天没跑完就放弃了。想自己写一个近重复检测的库。

判定的口径是按相似度阈值来的，阈值可配置。要求是召回和误报都要达标：samples 里那份带标注的数据集上，该抓出来的不能漏、不该抓的不能抓进来，门槛写在下面，差一点都算不过。内存是硬约束：几百万篇的规模，不许把所有文档的完整特征全堆在内存里，必须想办法分块处理，跑完的内存峰值要看得出来是可控的。结果要确定：同一份数据跑两遍，分组和组内顺序必须一样；每组用哪篇当代表也要有明确规则。边界情况要想到：空文档、只有几个字的、完全一样的，还有看起来像但其实无关的。量上，samples 里那份数据集要在几分钟内跑完。实现只用标准库，测试用 unittest。

仓库里只有这份说明和 samples 里的样例数据集与期望分组，代码从零写。

## 判定口径

1. **归一化**：去掉所有空白字符（空格、制表、换行等），ASCII 字母转小写，其余字符原样保留（**标点保留**，改动标点算改动）。
2. **特征**：归一化后取字符级 **3-gram**——从左到右滑动、每次取 3 个连续字符，重复的只算一次，得到一个集合。归一化后长度小于 3 时，整串就是唯一的特征；长度是 0（空文档）时特征集是**空集**。
3. **相似度**：Jaccard 系数 `|A ∩ B| / |A ∪ B|`。两个空集之间的相似度定义为 `1`（两篇空文档算完全一样）。
4. **判定**：相似度 `≥ 阈值 τ` 视为近重复；`τ` 默认 `0.8`，可配置。样例的期望分组就是按 `τ = 0.8` 算出来的。
5. **分组**：把「相似度 ≥ τ」当成一条边，最终的组是图的**连通分量**（传递闭包）。所以 A 与 B 相似、B 与 C 相似时，三者会在同一组，即使 A 与 C 的直接相似度没到阈值。

## 分片口径（内存约束）

几百万篇文档，任何一步都不许把所有文档的完整特征或所有文档对堆进内存。允许的做法包括：给每篇文档算固定长度的指纹（签名），按指纹分带分桶，把桶或签名落到临时文件再按块处理，按文档编号分块扫描等等。具体要求：

- **近似只能用来找候选**：指纹、分带、分桶都可以，但最终判定必须回到上一条的**精确 Jaccard** 上（用两篇文档的完整特征集重算）。这样结果与分块方式、分块顺序、指纹参数都无关，只与数据本身有关。
- **预算**：生产规模（几百万篇）下进程内存峰值不超过 **512 MB**；样例数据集（3000 篇）跑完不超过几分钟。
- 内存峰值要能被测出来（`tracemalloc` 之类的工具），测试里要有这一项。

## 门槛（在 samples 数据集上）

`samples/labels.csv` 是人工标注：`id_a,id_b,label`，`1` 表示这两篇是同一篇内容的变体（正例），`0` 表示确认无关（负例，包含一批「模板相近但其实无关」的）。

| 指标 | 定义 | 门槛 | 参考实现实测 |
| --- | --- | --- | --- |
| 召回 | 被判为同一组的正例对 / 正例对总数 | **≥ 0.95** | 1.00 |
| 误报 | 被判为同一组的负例对 / 负例对总数 | **= 0** | 0 |

误报是硬零：只要把一条负例对判进同一组就不算过。参考实现是「指纹找候选 + 精确 Jaccard 复核」，所以不会因为指纹碰撞引入误报。

## 分组与输出规则

- 每组用**组内编号最小**的那篇当代表。
- 输出一行一组，成员编号升序排列、逗号分隔，第一个就是代表；组与组之间按代表编号升序。
- **只输出成员数 ≥ 2 的组**，单篇文档不占行。
- 行尾 LF；同一份数据跑两遍，输出必须逐字节一样。

```text
1,2,3,4
5,6,7,8
```

## 边界情况

samples 里都构造了，实现要按下面的口径处理：

| 情况 | 期望 |
| --- | --- |
| 空文档（特征集为空） | 两篇空文档相似度为 1，会分到同一组；空文档与任何非空文档相似度为 0 |
| 只有几个字的文档（归一化后长度 < 3） | 整串作为唯一特征；完全相同的短文档会成组，只差一个字就不成组 |
| 完全一样的文档 | 相似度 1，必然成组 |
| 看起来像但其实无关（同一模板、不同主体词） | 相似度要低于阈值，不许成组——这是误报门槛里专门盯的一类 |

## 样例

```text
samples/docs.jsonl           3000 篇文档，每行 {"id":N,"text":"…"}
samples/labels.csv           标注对（id_a,id_b,label），402 条正例 + 800 条负例
samples/expected-groups.txt  τ = 0.8 下的期望分组（102 组）
```

数据集里包含 60 组「原文 + 3 篇轻改写」（含转载前缀、标点改动、尾部补充）、40 组完全重复、2 篇空文档、2 篇两字文档、6 篇模板相近的干扰文档，其余是互不相关的内容。期望分组由「精确 Jaccard + 连通分量」得到，并与构造时的真值逐组核对过。

## 用法

```bash
# 跑近重复检测，输出分组（τ 默认 0.8，可用 --threshold 改）
python -m neardup run samples/docs.jsonl -o groups.txt

# 在标注对上评估召回与误报
python -m neardup evaluate samples/labels.csv groups.txt

# 跑测试（unittest）
python -m unittest discover -s tests -v
```

输入是 jsonl，每行 `{"id":N,"text":"…"}`；id 假定唯一且能放进 64 位有符号整数。输出即上文「分组与输出规则」的格式。库用法：

```python
from neardup import Config, find_duplicate_groups
stats = find_duplicate_groups("docs.jsonl", "groups.txt", Config(threshold=0.8))
```

## 实现说明（原「待补的文档」）

### 指纹与分带参数

- 每个 3-gram 特征用 **blake2b（8 字节）** 算一个 64 位基哈希（标准库 `hashlib`，跨进程、跨平台确定，不依赖 `PYTHONHASHSEED`）。
- MinHash 签名长度 **192**，第 i 维是 `(a_i·h + b_i) mod 2^32` 在全特征集上的最小值；`a_i, b_i` 由固定种子的 `random.Random` 生成，完全确定。
- LSH 分带：**b = 32 带 × r = 6 行**，每带的 6 个签名值再压成一个 16 字节带键。两篇文档只要有一条带键相同就成为候选对。相似度 0.92（样例正例的最低档）的漏检概率约 `(1-0.92^6)^32 ≈ 1e-13`，可以忽略；相似度 0.35 的无关文档成为候选的概率只有约 6%。
- 另对每篇文档的归一化全文算一个 **128 位指纹**，用来把完全重复（含空文档）先折叠掉。

### 候选的分块流式产生

1. **顺序扫描**输入一遍：归一化文本追加写入临时文件（内存里只留每篇 8 字节偏移 + 4 字节特征数），同时流出两类定长记录——全文指纹记录（16 字节指纹 + 4 字节文档序号）和分带记录（16 字节带键 + 4 字节序号）。每篇文档产生 1 + 32 条记录，直接写盘，不在内存累积。
2. **外排序**（`neardup/externalsort.py`）：按 `chunk_records`（默认 100 万条）分块读入、块内排序、落临时文件、再多路归并流式输出。任何时刻内存里只有一个分块加归并堆，与记录总数无关。
3. 指纹记录排序后，相同指纹的文档（归一化文本完全一致，相似度恒为 1）直接在并查集里合并；后续候选配对只取每个完全重复组的**代表**，避免转载大户把桶撑爆。
4. 分带记录排序后按带键分桶，桶内两两配对写成候选对记录（8 字节），再外排序去重，逐对流式消费。候选对从产生到消费全程走临时文件，不堆内存。

### 精确复核只读两篇

候选对逐条复核：先用特征数做上界剪枝（`J ≤ min(|A|,|B|)/max(|A|,|B|)`，不够界直接跳过）；需要细算时，按偏移从临时文件**只读出这两篇**的归一化文本，现场重算 3-gram 集合，算精确 Jaccard，`≥ τ` 才合并。另配一个容量可配的 LRU 缓存（默认 1024 篇）吸收重复访问。因此最终判定只与数据本身有关，与分块方式、分块顺序、指纹参数无关。分组用基于 `array` 的并查集（几百万篇也只有几十 MB），连通分量即最终组。

### 内存峰值怎么测

`tests/test_memory.py` 用 `tracemalloc` 包住完整流程实测峰值：

- 4 000 / 8 000 篇合成文档（外排序分块刻意调到 5 万条，强制走多块归并），峰值均 **< 64 MB**——若把全部特征集堆进内存，同规模需要上百 MB；
- 文档数从 4 000 翻倍到 8 000 时，峰值从约 11 MB 涨到约 16 MB（远小于线性；若把全部特征堆进内存会严格线性增长）。测试断言峰值增长 **< 2 倍**，证明峰值由分块大小主导、与文档总量无关。

生产规模（几百万篇）的内存构成：每篇文档 8+4 字节索引 + 4 字节并查集 + 8 字节 id，合计约 24 字节/篇（4 百万篇 ≈ 100 MB），加上一个外排序分块（默认 100 万条 × 20 字节 ≈ 几十 MB）和复核缓存，总量在 **512 MB** 预算内；`chunk_records` 和 `cache_size` 是 `Config` 上现成的调压旋钮。

### 标注的一个细节

`samples/labels.csv` 里 `(201, 202)` 这一对同时被标了 `1` 和 `0`（其余 1200 对无冲突）。该对确实是同一内容的变体（期望分组里同组），评估时**以正例为准**，否则「误报 = 0」自相矛盾。`neardup/evaluate.py` 的 `load_labels` 实现了这个口径。
